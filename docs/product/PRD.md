# 产品需求
目标用户为3～5人软件团队：将自然语言需求转换为可审查的多Agent任务图，执行后交付带证据的方案、任务清单和审查报告。核心价值是模型参与规划、角色推理和修订，程序保障可执行性与终止。

## 用户闭环
创建项目→输入规格/约束/验收标准→选择REAL或TEST及模型→Planner生成计划→服务端校验→画布显示待确认计划→人工编辑与审批→真实执行→确定性验证→Reviewer→必要时审批修订→交付成果与轨迹。手动模式从空任务图开始，复用同一校验与执行链。AI优化返回patch和解释，用户选择接受；不得覆盖人工草稿。

P0：专业画布、Agent CRUD/版本、模型设置、自然语言拆解、Schema与DAG校验、有限并发、真实工具与模型、人工审批、暂停调度/取消、输出审查、一次修订演示、持久化和断线恢复。P1：通用局部重规划、并发调优、回放、模板、成本图表和局部重试。P2：长期记忆/RAG/MCP/市场。明确排除分布式、多租户和支付。

验收区别：计划有效≠执行成功≠结果合格。COMPLETED要求全部必需任务完成、确定性验证通过、最终review为pass。部分成功可以下载成果，但不能显示整体完成。无联网工具的Research仅分析输入和已有知识，界面标记未联网，不能输出虚构检索记录。

## 演示规格
输入“设计团队缺陷跟踪工具：项目、缺陷、负责人、状态流转；Windows本地；给出接口、开发任务和测试方案”。Planner生成R技术研究与Q验收分析并行；R完成后提出向Architecture交接（目标、artifact与reason），编排器接受后Architecture消费R方案与Q约束；Planning消费Architecture接口生成开发任务；TestDesign消费接口与Q标准生成测试矩阵，两者并行；Reviewer消费所有成果及确定性覆盖率报告。漏掉状态流转测试时，输出revise及criterion_id，人工批准追加TestDesign修订任务，再审查并汇总。

结构化产物依次为sources/options、criteria、modules/interfaces、tasks/dependencies、cases/coverage、review/findings。最终提供设计Markdown、任务JSON、测试矩阵和审查JSON；本期不声称生成的软件已实现。演示具体依赖见编排引擎。用户尚未提供可见参考截图，UI设计以文档原则为依据，像素匹配待后续材料。
